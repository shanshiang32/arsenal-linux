# Makefile 和 Git：从零理解到课堂演示

## 1. 先区分它们解决的问题

假设项目只有一个 `main.cpp`，你可以直接执行：

```bash
g++ main.cpp -o game
```

现在我们有五个 `.cpp` 文件，还有头文件、测试和不同编译模式。每次手写所有编译命令容易漏文件，也会重复编译没有修改的代码。Makefile 用来写下构建规则，由 `make` 工具执行。

随着修改增多，你还会遇到“昨天的代码是怎样的”“这个功能改了哪些地方”“改坏了怎么撤回”。Git 用来保存、比较和组织代码版本。

| 工具 | 管理对象 | 本项目中的实际用途 |
|---|---|---|
| Make / Makefile | 构建任务与文件依赖 | 编译、链接、增量构建、测试、清理、打包 |
| Git | 代码版本与分支历史 | 提交、差异、分支、合并、版本标签 |

Makefile 是规则文件，Make 是读取它的工具。Git 是版本管理工具，GitHub 是可托管Git仓库的平台；没有GitHub、没有网络也能使用本项目的Git功能。

## 2. 源码怎样变成可执行程序

本项目的过程是：每个 `.cpp` 分别编译成 `.o` 目标文件，再把这些目标文件链接成 `arsenal`。头文件一般通过 `#include` 被源码使用，不是单独拿来生成可执行文件。

例如：

```bash
g++ -Iinclude -std=c++17 -c src/engine.cpp -o engine.o
g++ main.o engine.o model.o storage.o ui.o -o arsenal
```

第一行只编译；第二行链接。`.o` 可以保留下来，下次只编译改动影响到的模块。

## 3. Makefile的基本语法

```make
目标: 依赖
	命令
```

上面的 `\t` 表示实际的 **Tab字符**，不能直接输入反斜杠加字母t，也不要用空格替代。项目已经放好了正确的Tab。

```make
$(BUILD)/%.o: src/%.cpp Makefile
	@mkdir -p $(@D)
	$(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@
```

这是本项目的模式规则。例如目标为 `build/release/engine.o` 时，`%` 就是 `engine`。

| 记号 | 含义 | 在这个例子中 |
|---|---|---|
| `$@` | 当前目标 | build/release/engine.o |
| `$<` | 第一个依赖 | src/engine.cpp |
| `$(@D)` | 目标所在目录 | build/release |
| `$^` | 所有依赖，去重 | 链接规则中的全部目标文件 |
| `@命令` | 执行时不打印命令本身 | 只隐藏mkdir命令，不隐藏错误 |

Make通常根据依赖文件的修改时间判断目标是否过期。若目标不存在，或某个依赖比目标新，就执行规则。

## 4. 本项目Makefile的设计思路

### 4.1 用变量集中管理编译设置

```make
CXX ?= g++
MODE ?= release
CPPFLAGS += -Iinclude
CXXFLAGS += -std=c++17 -Wall -Wextra -Wpedantic -Wconversion -MMD -MP
```

`?=` 表示尚未设置时提供默认值，命令行可以用 `make CXX=clang++` 选择其他编译器。`-Iinclude` 指定头文件搜索目录；`-Wall`等打开警告。

Debug使用 `-O0 -g3`，Release使用 `-O2 -DNDEBUG`。Debug方便单步调试，Release偏重运行效率。它们的输出目录不同，不会混用目标文件。

### 4.2 自动搜集源文件并转换路径

```make
SOURCES := $(wildcard src/*.cpp)
OBJECTS := $(patsubst src/%.cpp,$(BUILD)/%.o,$(SOURCES))
```

`wildcard`得到所有源文件；`patsubst`把每个源文件路径转换为对应目标文件路径。以后增加一个普通 `.cpp` 模块，不用再手写一条编译规则。

### 4.3 先分别编译，再统一链接

```make
$(TARGET): $(OBJECTS)
	$(CXX) $^ $(LDFLAGS) -o $@
```

程序依赖全部目标文件。只要某个目标文件更新，就重新链接。`make -j4`允许最多四个任务并行，Make会根据依赖关系确保链接在编译完成后执行。

### 4.4 自动跟踪头文件依赖

`-MMD`让编译器在生成 `.o` 时也生成 `.d` 依赖文件；`-MP`给头文件添加空规则，减少头文件删除时的依赖报错。

```make
-include $(OBJECTS:.o=.d) $(BUILD)/test.d
```

Make读取这些 `.d`，知道哪个 `.cpp` 使用了哪个头文件。开头的减号表示首次构建时 `.d` 不存在也不报错。

例如修改 `engine.hpp` 后，引擎、入口和界面等使用它的模块会重新编译；`storage.cpp`不依赖它，就无需重新编译。这个“按依赖重建”的能力，比简单地写一条编译所有源文件的命令更能体现Make的价值。

### 4.5 把常用任务做成伪目标

`.PHONY`表示这些名字是任务，不是同名文件。即使目录里出现名为 `test` 的文件，`make test`仍会执行测试。

| 命令 | 实际目的 |
|---|---|
| `make` | 默认构建Release |
| `make run` | 必要时先构建，再启动 |
| `make demo` | 临时存档自动展示主要功能 |
| `make test` | 编译并执行核心测试及命令行测试 |
| `make debug` | 用递归Make构建Debug |
| `make sanitize` | 检查内存和未定义行为 |
| `make clean` | 删除构建产物 |
| `make dist` | 打包纯源码，不含Git历史 |

## 5. Git的基本思路：三个位置

- 工作区：你正在编辑的文件。
- 暂存区：你准备放进下一次提交的改动。
- 本地仓库：已提交的版本历史，保存在 `.git` 中。

```bash
git status                 # 查看哪些文件有变化
git diff                   # 查看未暂存的改动
git add src/engine.cpp     # 选择要暂存的文件
git diff --cached          # 查看本次准备提交的内容
git commit -m "修复交易结算" # 保存一个版本快照
```

`git add`还没有生成历史版本；`git commit`才会创建提交。每次提交应是一组有明确目的的改动，而不是为了凑数量随意提交。

Git不会自动替你运行Make。本项目把两者配合使用：改代码 → `make test` → 检查差异 → Git提交。

## 6. 为什么要用分支和合并

分支可以理解为指向一串提交末端的名字。例如主线保留稳定功能，在 `feature/statistics` 开发统计实验，通过测试后合并回主线。

```bash
git switch -c feature/my-feature
# 编辑相关代码
make test
git add src/相关文件.cpp
git commit -m "增加某项功能"
git switch main
git merge --no-ff feature/my-feature
```

上面是开发流程示意，`src/相关文件.cpp`需要替换为真实文件名。`--no-ff`保留一次明确的合并提交，图形日志更便于演示。多人修改同一段代码时可能产生冲突，需要人工选择正确结果、测试、再提交；本次交付没有制造冲突。

项目中已经实际创建 `feature/statistics` 与 `feature/quality` 并合并。可以直接查看：

```bash
git log --all --graph --oneline --decorate
git branch
git show feature/statistics --stat
git show feature/quality --stat
git diff v0.1-core..v1.0 --stat
```

标签 `v0.1-core`、`v1.0`给重要版本一个稳定易读的名字。分支通常随新提交向前移动，标签通常固定标记一个发布版本。

## 7. .gitignore为什么重要

本项目忽略 `build/`、`dist/`和存档。它们属于可重新生成的文件或个人运行数据。Git保留源码、规则和文档，就可以在另一台Linux机器上重新构建。

`.gitignore`对已被Git跟踪的文件不会自动解除跟踪。本项目从首次提交就没有跟踪构建产物和个人存档。

## 8. 课堂演示：约8至12分钟

### 第一步：说明结构（1分钟）

打开README，介绍五个模块和职责。说明不是把所有功能塞到一个 `main.cpp` 中。

### 第二步：演示编译与增量构建（2分钟）

```bash
make clean
make -j4
make
```

第一次出现五条编译命令和一条链接命令；第二次一般显示无需执行任务。

```bash
touch src/engine.cpp
make
```

`touch`只改变修改时间。此时应只重编译 `engine.cpp`，然后重新链接。Git按内容比较，`git status`仍可保持干净。

```bash
touch include/engine.hpp
make
```

这次会重编译引用这个头文件的多个模块，说明 `.d` 自动依赖生效。

### 第三步：演示游戏（2分钟）

```bash
make demo
```

脚本依次展示箱子、领取补给、五连开箱、背包、锁定后拒绝出售、统计和十万次概率实验。全部使用临时存档，可以重复运行。

### 第四步：演示质量检查（1分钟）

```bash
make test
make debug
```

解释测试覆盖余额扣除、锁定保护、每日领取、随机复现、存档往返、损坏存档、进程锁等，而不只是“程序能打开”。

### 第五步：展示Git历史（2分钟）

```bash
git status
git log --all --graph --oneline --decorate
git show feature/statistics --stat
git diff v0.1-core..v1.0 --stat
git tag
```

解释提交、分支、合并与版本标签。说明这是助手在制作中生成的演示历史，自己应能解释其中代码。

### 第六步：现场做一条自己的提交（可选，2分钟）

先在 `git status` 中确认没有待处理改动。以下只创建新分支并新增说明文件，不修改游戏：

```bash
git switch -c classroom/demo
printf '我的课堂演示笔记\n' > docs/课堂笔记.md
git status
git diff --no-index /dev/null docs/课堂笔记.md
# 上条命令发现差异时返回1是正常的。
git add docs/课堂笔记.md
git diff --cached
git -c user.name='Student Demo' -c user.email='student@example.invalid' commit -m 'docs: add classroom notes'
git switch main
git merge --no-ff classroom/demo -m 'merge: classroom demonstration'
git log --graph --oneline -8
```

若已经创建过同名分支，下次请换一个新名字；如自己的Git尚未配置身份，合并前按下一节设置仓库内身份。

## 9. 真实使用时的身份与远程仓库

当前仓库使用 `Arsenal Demo <demo@example.invalid>`，仅用于展示。后续自己开发，可以在项目目录设置自己的身份（不加 `--global`，只作用于当前仓库）：

```bash
git config user.name '你的名字'
git config user.email '你的邮箱'
```

需要交到GitHub/Gitee时，先自行创建远程空仓库，再使用真实URL：

```bash
git remote add origin 你的远程仓库URL
git push -u origin main
git push origin --tags
```

以上远程命令没有在交付环境执行。Git本身的版本管理和本地分支功能不需要远程账号。

## 10. 可能被老师问到的问题

**Makefile和Shell脚本有何区别？** Shell脚本通常按顺序执行命令；Makefile描述目标依赖，Make判断哪些目标过期、按依赖顺序执行，也支持并行。

**为什么改头文件也会触发编译？** 编译器生成 `.d`记录头文件依赖，Make读取后判断相关目标过期。

**Git会保存可执行文件吗？** 可以，但本项目选择忽略构建产物，保存可重建它们的源码和构建规则。

**如何看旧代码？** 可以 `git show v0.1-core:src/engine.cpp`只读查看旧文件；不必改动当前工作区。

**如何撤销已经提交的一次改动？** 通常使用 `git revert 提交ID`创建一个反向提交，再运行测试。这会保留历史。不要在还没理解之前使用 `git reset --hard`，它可能丢弃工作区改动。

**为什么开箱程序适合展示？** 随机抽样、数据模型、排序筛选、交易结算、文件读写、互斥锁、错误处理、测试都能分成独立模块，因此Make依赖图和Git功能分支都有实际用途。
